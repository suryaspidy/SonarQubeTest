Variant 1 — Default / Unchanged Admin Credentials

CWE-16 · POST /api/a02/admin-login

The admin console was installed with a well-known default username/password, and nobody ever rotated it.

—
Fix: force a credential change (or disable the account) on first boot as part of a repeatable hardening/install process — never ship a reachable default password.

Variant 2 — Directory Listing Enabled + Exposed Backup/Config Files

CWE-16 (commonly CWE-548 / CWE-530) · GET /api/a02/directory-listing

A "legacy uploads" folder was mounted with directory listing and dotfiles both left enabled — exposing a stale .env backup, a database dump, and internal notes.

—

Click a file's URL in the output above (or open it directly) to download the real exposed file.

Fix: disable directory listing, never allow dotfiles on a public static mount, and keep backups/config entirely outside the web root.

Variant 3 — Verbose Error Messages / Stack Trace Disclosure

CWE-16 (commonly CWE-209 / CWE-215) · GET /api/a02/trigger-error

No central error handler sanitizes failures here — the raw stack trace, file paths, and runtime version are sent straight to the client.

—
Fix: centralize error handling; log full details internally, but return only a generic message + correlation ID to the client.

Variant 4 — Active Debug Code Left Enabled in Production

CWE-489 / CWE-11 · GET /api/a02/debug/eval

A developer convenience endpoint for evaluating expressions was gated behind a DEBUG_MODE flag meant to default to false in production — it was never flipped off.

—
Fix: debug/diagnostic endpoints must be compiled out or feature-flagged per-environment via a deployment pipeline, never a source-level default that can be "forgotten".

Variant 5 — Sensitive Information Exposure via Environment Variables

CWE-526 · GET /api/a02/debug/env

A diagnostics endpoint meant for local troubleshooting dumps the full environment — database credentials, cloud/API secrets — with no authentication.

—
Fix: never expose raw environment variables over HTTP; if a health/diagnostics endpoint is needed, redact anything secret-shaped and require authentication.

Variant 6 — Use of a Hard-Coded, Security-Relevant Constant

CWE-547 · GET /api/a02/premium-report

A "premium" feature is gated by a hard-coded internal bypass token meant only for QA — a static string baked into the source (and, as it happens, also sitting in Variant 2's exposed files).

—
Fix: never use static, source-embedded tokens to gate security-relevant behavior — use per-environment secrets from a manager/KMS, or remove the bypass entirely.

Variant 7 — Sensitive Cookie Missing Secure / HttpOnly / SameSite

CWE-614 / CWE-1004 · GET /api/a02/admin-session

An admin session cookie is issued with none of the attributes that protect it in transit or from script access.

—
Fix: set Secure, HttpOnly, and an appropriate SameSite value on every session/auth cookie, with no exceptions.

Variant 8 — Overly Permissive Default Cloud Storage Permissions

CWE-16 · GET /api/a02/cloud-bucket

A mock object-storage bucket where every object defaulted to "public-read" on upload, and nobody ever tightened the policy.

—
—
Fix: default new storage objects/buckets to private; require an explicit, reviewed policy change to make anything public; audit cloud storage ACLs regularly.

Variant 9 — XML External Entity (XXE) Injection via Misconfigured Parser

CWE-611 / CWE-776 · POST /api/a02/xxe-parse

The XML parser resolves DOCTYPE external entities by default — a configuration flaw. Try the default payload, which reads a file on the server and inlines its contents into the response.

—

Try changing the SYSTEM path to escape further, e.g. file:///../server.js.

Fix: disable DTD processing and external entity resolution in the XML parser (most modern libraries default to safe, but must be explicitly verified) — never trust parser defaults.

📘 Deep Dive: OWASP A02:2025 — Security Misconfiguration

Security Misconfiguration jumped from #5 in the 2021 edition to #2 in OWASP's Top 10:2025 — the biggest riser on the list, driven by the explosion of highly configurable cloud services, containers, and Infrastructure as Code.

1. What Counts as "Security Misconfiguration"?

Per OWASP, an application may be vulnerable if:

  • It is missing appropriate security hardening anywhere in the stack, or has improperly configured cloud service permissions.
  • Unnecessary features are enabled or installed (unused ports, services, pages, accounts, testing frameworks, or privileges).
  • Default accounts and their passwords are still enabled and unchanged.
  • There's no central handling for excessive error messages — stack traces or overly informative errors reach users.
  • For upgraded systems, the latest security features are disabled or not configured securely.
  • Backward-compatibility is prioritized over secure configuration.
  • Security settings in app servers, frameworks (Struts, Spring, ASP.NET, …), libraries, and databases aren't set to secure values.
  • The server doesn't send security headers/directives, or sends insecure ones.

2. The Variants

This lab implements 9 variants, chosen to mirror OWASP's own example attack scenarios and its two headline CWEs (CWE-16 Configuration, CWE-611 XXE). Expand each for the mechanism, vulnerable code, and how it's exploited:

Variant 1 — Default / Unchanged Admin Credentials CWE-16

OWASP Example Attack Scenario #1: "The application server comes with sample applications not removed from the production server... Suppose one of these applications is the admin console, and default accounts weren't changed. In that case, the attacker logs in with the default password and takes over."

Node.js — data/misconfig-store.js (vulnerable, this app)
const adminAccount = { username: 'admin', password: 'admin', rotated: false };

Attack scenario: an attacker tries the well-known default credentials for the platform/framework in use (admin/admin, root/toor, etc.) against the login form — no brute force required, because it was never changed after install.

Variant 2 — Directory Listing Enabled + Exposed Backup/Config Files CWE-16 / CWE-548 / CWE-530

OWASP Example Attack Scenario #2: "Directory listing is not disabled on the server. An attacker discovers they can simply list directories... The attacker finds and downloads the compiled Java classes, which they decompile and reverse engineer to view the code."

Node.js — server.js (vulnerable, this app)
// A second static mount with dotfiles explicitly allowed — no exclusions:
app.use('/legacy-uploads', express.static(path.join(__dirname, 'misconfigured-uploads'), { dotfiles: 'allow' }));

Attack scenario: the "List /legacy-uploads/" button above returns a stale .env.backup (database + cloud credentials), a forgotten SQL dump, and internal notes — none of which should ever have been reachable over HTTP.

Variant 3 — Verbose Error Messages / Stack Trace Disclosure CWE-16 / CWE-209 / CWE-215

OWASP Example Attack Scenario #3: "The application server's configuration allows detailed error messages, such as stack traces, to be returned to users. This potentially exposes sensitive information or underlying flaws, such as component versions that are known to be vulnerable."

Node.js — routes/a02.js (vulnerable, this app)
catch (err) {
  res.status(500).json({ error: err.message, stack: err.stack, nodeVersion: process.version, cwd: process.cwd() });
}

Attack scenario: an attacker deliberately sends malformed input to trigger an exception, then reads the returned stack trace to learn internal file paths, the exact framework/runtime version (letting them look up known CVEs for that version), and clues about the app's internal structure.

Variant 4 — Active Debug Code Left Enabled in Production CWE-489 / CWE-11

Mechanism: a developer-only debug endpoint (here, an arbitrary expression evaluator) is gated behind a flag that was supposed to be disabled before shipping to production — the "TODO" to flip it off was never completed.

Node.js — routes/a02.js (vulnerable, this app)
const DEBUG_MODE = true; // TODO: set to false before deploying — never done

if (DEBUG_MODE) {
  router.get('/debug/eval', (req, res) => {
    const result = eval(req.query.expr); // arbitrary code execution
    res.json({ result });
  });
}

Attack scenario: the button above sends require('os').hostname() as the expression — proving arbitrary Node.js code execution is reachable in what's supposed to be a production deployment.

Variant 5 — Sensitive Information Exposure via Environment Variables CWE-526

Mechanism: a diagnostics/health-check endpoint intended for local troubleshooting was left reachable in production and dumps the full environment with no redaction.

Node.js — routes/a02.js (vulnerable, this app)
router.get('/debug/env', (req, res) => {
  res.json({ env: store.simulatedProdEnv }); // no auth, no redaction
});

Attack scenario: a single unauthenticated request returns database credentials, a JWT signing secret, and cloud/API keys — everything needed to pivot into the rest of the infrastructure.

Variant 6 — Use of a Hard-Coded, Security-Relevant Constant CWE-547

Mechanism: a feature gate (here, a "premium" report) can be bypassed with a static, source-embedded token that was meant only for internal QA use.

Node.js — routes/a02.js + data/misconfig-store.js (vulnerable, this app)
const INTERNAL_BYPASS_TOKEN = 'lab-internal-9f3a';
// ...
if (req.header('X-Internal-Bypass') === INTERNAL_BYPASS_TOKEN) { /* unlock premium content */ }

Attack scenario: the token leaked into the exposed internal-notes.txt from Variant 2 — once an attacker has it, sending it as a header unlocks paid functionality for free, permanently, for anyone.

Variant 7 — Sensitive Cookie Missing Secure / HttpOnly / SameSite CWE-614 / CWE-1004

Mechanism: a session cookie is issued without the attributes that protect it — Secure (HTTPS-only), HttpOnly (hidden from JavaScript), and SameSite (cross-site request restriction).

Node.js — routes/a02.js (vulnerable, this app)
res.cookie('admin_session', 'admin-session-demo-token', {}); // no flags at all

Attack scenario: without HttpOnly, any XSS elsewhere in the app can read this cookie directly via document.cookie; without Secure, it can be intercepted if the connection is ever downgraded to plain HTTP; without SameSite, it's attached to cross-site requests (feeding straight into CSRF, as seen on the A01 screen).

Variant 8 — Overly Permissive Default Cloud Storage Permissions CWE-16

OWASP Example Attack Scenario #4: "A cloud service provider (CSP) defaults to having sharing permissions open to the Internet. This allows sensitive data stored within cloud storage to be accessed."

Node.js — data/misconfig-store.js (vulnerable, this app)
const cloudBucket = [
  { key: 'customer-exports/2026-01-report.csv', acl: 'public-read', content: '...' },
  // every object defaulted to public-read on upload, and nobody tightened it
];

Attack scenario: tools exist purely to enumerate publicly-readable cloud storage buckets across the internet; once found, every object inside — customer exports, database snapshots, financial spreadsheets — is downloadable with zero credentials, exactly as demonstrated above.

Variant 9 — XML External Entity (XXE) Injection via Misconfigured Parser CWE-611 / CWE-776

Mechanism: the XML parser processes <!DOCTYPE> declarations and resolves external entities (SYSTEM "file://...") by default — a parser configuration issue, which is exactly why OWASP files it under Security Misconfiguration rather than Injection, even though the payload looks similar to an injection attack.

XML — malicious payload
<?xml version="1.0"?>
<!DOCTYPE data [ <!ENTITY xxe SYSTEM "file:///private/secrets.txt"> ]>
<data>&xxe;</data>

Attack scenario: submitting this XML to any endpoint that parses it with external entities enabled causes the parser to read the referenced local file and splice its contents directly into the parsed output — exactly what the demo above does, using this app's own private/secrets.txt (created for the A01 screen) as the target file.

3. How to Prevent It (per OWASP)

  • A repeatable hardening process that deploys another environment already locked down; dev/QA/production configured identically, with different credentials per environment, automated to minimize setup effort.
  • A minimal platform with no unnecessary features, components, documentation, or samples — remove unused features and frameworks rather than just disabling them.
  • A recurring task to review and update configuration alongside every security patch (see A04: Cryptographic Failures for key rotation, and the upcoming A03: Software Supply Chain Failures for patch management). Review cloud storage permissions (e.g. S3 bucket policies).
  • A segmented architecture with effective separation between components/tenants (segmentation, containerization, cloud security groups/ACLs).
  • Sending security directives to clients — i.e. security headers.
  • An automated process to verify configuration effectiveness in every environment; if not automated, verify manually at least annually.
  • A central configuration to intercept excessive/overly-detailed error messages as a backstop.
  • Identity federation, short-lived credentials, or platform-native role-based access instead of embedding static keys/secrets in code, config files, or pipelines.
