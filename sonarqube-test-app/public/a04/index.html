Variant 1 — Cleartext Storage of Sensitive Data at Rest

CWE-312 / CWE-313 · GET /api/a04/payment-methods

Stored payment methods, straight from the "database" — full card numbers and CVVs as plain strings, exactly like a stolen backup or an over-privileged internal tool would see them.

—
Fix: never store CVVs at all (PCI-DSS forbids it post-auth); encrypt card numbers at the field level or use a tokenization provider; mask on display.

Variant 2 — Weak / Broken Hashing Algorithm for Passwords

CWE-327 / CWE-759 · GET /api/a04/weak-hash-users · POST /api/a04/crack-hash

Passwords hashed with unsalted MD5 — fast and pattern-prone. A tiny common-password dictionary cracks them instantly.

—
—
Fix: use a slow, salted, purpose-built password hash (bcrypt, scrypt, or Argon2id) with a per-user salt and a tuned work factor.

Variant 3 — Reversible Encryption Instead of a One-Way Hash for Passwords

CWE-328 · GET /api/a04/legacy-users · GET /api/a04/legacy-users/:id/decrypt

These "legacy" passwords are encrypted, not hashed — which means the original plaintext can be recovered by anyone holding the key (see Variant 4).

—
—
Fix: passwords must be hashed (one-way), never encrypted (two-way). If original plaintext must ever be recoverable, that's a sign it shouldn't be a "password" field at all.

Variant 4 — Hard-Coded Cryptographic Keys & Secrets

CWE-321 / CWE-798 · GET /api/a04/leaked-config

Simulates a leaked debug/config endpoint (or a secret committed to source control) exposing the exact key that decrypts every record in Variant 3, all at once.

—
Fix: never hard-code keys in source. Use a secrets manager / KMS, rotate keys, and scope them so no single leak compromises the entire dataset.

Variant 5 — Insecure Cryptographic Mode (ECB) / Broken Algorithm

CWE-327 / CWE-326 · POST /api/a04/ecb-demo

ECB mode encrypts each block independently — identical plaintext always produces identical ciphertext. Try the same PIN for both fields, then try different ones.

—

Same PIN twice: ECB ciphertexts match (pattern leak). CBC+random IV ciphertexts never match, even for identical input.

Fix: never use ECB. Use an authenticated mode with a random IV/nonce per message (e.g. AES-256-GCM), and never reuse a nonce with the same key.

Variant 6 — Missing Encryption in Transit / Insecure Cookie Attributes

CWE-319 / CWE-523 · GET /api/a04/security-headers

The app runs on plain HTTP with no HSTS, and sets a "remember me" cookie with none of the flags that protect it in transit or from script access.

—
Fix: serve everything over HTTPS, send Strict-Transport-Security, and set Secure + HttpOnly + SameSite on every session/auth cookie.

Variant 7 — Insecure Randomness for a Security Token (Brute-Forceable Password Reset)

CWE-330 / CWE-338 · POST /api/a04/reset/request · POST /api/a04/reset/verify

The reset code is generated with Math.random() (not a CSPRNG), is only 3 digits, never expires, and the verify endpoint has no rate limiting — brute-forceable in under a second.

—
—
Fix: generate tokens with a CSPRNG (crypto.randomInt / crypto.randomBytes), make them long, expire them quickly, and rate-limit/lock out the verify endpoint.

Variant 8 — Improper Certificate / TLS Validation on Outbound Requests

CWE-295 · GET /api/a04/tls-check

Compares a properly-validating HTTPS client against one configured with rejectUnauthorized:false, against badssl.com's public test certificates. Requires the server to have outbound internet access.

—
Fix: never set rejectUnauthorized:false (or an equivalent) in production. Pin certificates/CAs if needed, but always validate the chain and hostname.

Variant 9 — Sensitive Data Exposure via Logging

CWE-532 · POST /api/a04/legacy-login · GET /api/a04/logs

A "helpful" debug log line records the raw username and password on every login attempt — and this app then exposes those logs with no access control at all.

—
Fix: never log credentials, tokens, or other secrets. Redact/mask sensitive fields before they reach any logger, and restrict log access.

Variant 10 — Sensitive Data Exposed in a URL (Query String)

CWE-598 · POST /api/a04/magic-link

A "magic login" link carries the raw session token as a URL query parameter. URLs like this land in access logs, browser history, and Referer headers — in plaintext.

—
Fix: put tokens in the request body, an Authorization header, or a short-lived signed cookie — never in a URL that will be logged, cached, bookmarked, or shared.

2. The Variants

This lab implements 10 variants — expand each for the mechanism, vulnerable code, and how it's exploited:

Variant 1 — Cleartext Storage of Sensitive Data at Rest CWE-312 / CWE-313

Mechanism: sensitive fields (full card numbers, CVVs, government IDs) are written to the database exactly as received — no field-level encryption, no tokenization, no masking on read.

Impact: anyone with database/backup read access (a DBA, a misconfigured backup bucket, a SQL injection elsewhere in the app) gets the raw sensitive data with no extra step required.

Node.js — data/crypto-store.js (vulnerable, this app)
const paymentMethods = [
  { id: 1, user: 'alice', cardNumber: '4111111111111111', cvv: '123', expiry: '04/27' },
  // ...stored, queried, and returned exactly like this — no encryption, no masking
];

Attack scenario: an internal tool (or an attacker who reaches the database another way) calls GET /api/a04/payment-methods and receives full card numbers and CVVs in the clear — the kind of data breach that triggers PCI-DSS fines and mandatory disclosure.

Variant 2 — Weak / Broken Hashing Algorithm for Passwords CWE-327 / CWE-759

Mechanism: passwords are hashed with MD5 (designed for speed and checksums, not secrecy) and no per-user salt, so two users with the same password get the identical hash.

Impact: unsalted, fast hashes are crackable via precomputed rainbow tables or simple dictionary attacks in milliseconds — MD5 hardware-accelerated cracking now exceeds billions of hashes per second.

Node.js — data/crypto-store.js (vulnerable, this app)
function md5(input) {
  return crypto.createHash('md5').update(input).digest('hex');
}
const weakHashUsers = [
  { id: 2, username: 'bob', passwordHash: md5('letmein') }, // no salt, fast algorithm
];

Attack scenario: an attacker who obtains the hash list runs it against a common-password dictionary (this lab uses ~12 entries; real attacks use billions). Any user who chose a common password is cracked instantly — that's exactly what POST /api/a04/crack-hash demonstrates.

Variant 3 — Reversible Encryption Instead of a One-Way Hash for Passwords CWE-328

Mechanism: instead of hashing passwords (which can never be reversed), the app encrypts them with AES — a two-way operation. Anyone with the key can recover the original password.

Impact: defeats the entire point of "protecting" the password. A hash breach only exposes hashes (which still require cracking); an encryption-key breach exposes every password instantly and exactly as typed.

Node.js — data/crypto-store.js (vulnerable, this app)
function legacyEncrypt(plaintext) {
  const cipher = crypto.createCipheriv('aes-256-cbc', HARD_CODED_KEY, HARD_CODED_IV);
  return Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()]).toString('hex');
}
function legacyDecrypt(hex) {
  const decipher = crypto.createDecipheriv('aes-256-cbc', HARD_CODED_KEY, HARD_CODED_IV);
  return Buffer.concat([decipher.update(Buffer.from(hex, 'hex')), decipher.final()]).toString('utf8');
}

Attack scenario: with the key from Variant 4 (or just by reading the source), GET /api/a04/legacy-users/1/decrypt returns dave's original plaintext password directly — no cracking, no guessing, just decryption.

Variant 4 — Hard-Coded Cryptographic Keys & Secrets CWE-321 / CWE-798

Mechanism: the AES key and IV used everywhere in this app are constants baked directly into the source file — the same thing as committing them to git, or leaving a debug endpoint that echoes them back.

Impact: a single leak (a public GitHub repo, a decompiled mobile app, a support ticket with a stack trace, or — as demonstrated here — a debug endpoint) compromises every record ever encrypted with that key, all at once, forever (until the key is rotated and everything re-encrypted).

Node.js — data/crypto-store.js (vulnerable, this app)
const HARD_CODED_KEY = crypto.createHash('sha256').update('lab-super-secret-key-2021').digest();
const HARD_CODED_IV = Buffer.from('0123456789abcdef'); // static, reused for every record

Attack scenario: GET /api/a04/leaked-config hands the key and IV straight to the caller — from here, every "legacy" password in Variant 3 and every PIN in Variant 5 can be decrypted offline, with no further access to the app required.

Variant 5 — Insecure Cryptographic Mode (ECB) / Broken Algorithm CWE-327 / CWE-326

Mechanism: AES in ECB mode encrypts each fixed-size block independently with no chaining and no IV — identical plaintext blocks always produce identical ciphertext blocks.

Impact: without ever breaking the key, an observer can tell which records share the same underlying value (the classic demonstration is encrypting an image in ECB mode — the outline remains visible in the ciphertext).

Node.js — data/crypto-store.js (vulnerable, this app)
function ecbEncrypt(plaintext) {
  const cipher = crypto.createCipheriv('aes-256-ecb', HARD_CODED_KEY, null); // no IV — that's the flaw
  return Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()]).toString('hex');
}

Attack scenario: two users both pick the PIN "1234". Their "encrypted" values are byte-for-byte identical. An attacker who has compromised the ciphertext store (but not the key) can still cluster users by shared secret values — e.g. flag every account using the most common PIN, without decrypting anything.

Variant 6 — Missing Encryption in Transit / Insecure Cookie Attributes CWE-319 / CWE-523

Mechanism: the app is served over plain HTTP with no HTTP Strict-Transport-Security header, and session/"remember me" cookies are set without Secure, HttpOnly, or SameSite.

Impact: credentials and session tokens can be intercepted in transit on any shared or hostile network (public wifi, a compromised router, a malicious proxy); without Secure a cookie set once over HTTPS can still leak if the user is ever downgraded to HTTP; without HttpOnly it's readable by any injected script (pairs badly with an XSS bug elsewhere).

Node.js — routes/a04.js (vulnerable, this app)
// Vulnerable: no Secure, no HttpOnly, no SameSite
res.cookie('remember_me', 'token-in-cleartext-demo', {});

Attack scenario: an attacker on the same coffee-shop wifi runs a packet sniffer; the cookie and any HTTP-transmitted credentials appear in plaintext in the capture, ready to be replayed.

Variant 7 — Insecure Randomness for a Security Token CWE-330 / CWE-338

Mechanism: the password-reset code is generated with Math.random() — a fast, statistically-biased PRNG never intended for security use — producing only a 3-digit code (1,000 possibilities), with no expiry and no rate limit on verification.

Impact: the entire keyspace can be exhausted client-side in well under a second, letting an attacker take over any account via "forgot password" without ever seeing the real code.

Node.js — data/crypto-store.js (vulnerable, this app)
function generateWeakResetToken() {
  // Math.random() is not cryptographically secure, and 3 digits is tiny
  return String(Math.floor(Math.random() * 1000)).padStart(3, '0');
}

Attack scenario: the "Brute-force all 1,000 possible codes" button above does exactly this: it fires all 1,000 guesses at POST /api/a04/reset/verify with no lockout in place, and reports back the moment one succeeds.

Variant 8 — Improper Certificate / TLS Validation on Outbound Requests CWE-295

Mechanism: an HTTPS client is configured with rejectUnauthorized:false (or the equivalent in another language/library), which disables certificate chain, expiry, and hostname verification entirely.

Impact: the connection is still "encrypted" in the sense that traffic is scrambled, but there's no guarantee it's scrambled to the intended server — a machine-in-the-middle presenting any certificate (expired, self-signed, for the wrong domain) is accepted without complaint.

Node.js — routes/a04.js (vulnerable, this app)
const agent = new https.Agent({ rejectUnauthorized: false }); // disables cert validation entirely
https.get(url, { agent }, (res) => { /* ... */ });

Attack scenario: this pattern is common in "fix it later" workarounds for expired internal certificates. An attacker positioned on the network path (compromised wifi, DNS hijack, malicious proxy) presents their own certificate for the target host; the vulnerable client accepts it and happily sends requests through the attacker.

Variant 9 — Sensitive Data Exposure via Logging CWE-532

Mechanism: a debug/troubleshooting log statement records complete request data — including passwords — verbatim, and that log is either broadly accessible or exposed by another bug (as demonstrated here, an unauthenticated endpoint).

Impact: logs are often replicated to multiple systems (log aggregators, SIEMs, ticketing systems attached to error reports, developer laptops during debugging) — far more copies, with far looser access control, than the primary database.

Node.js — routes/a04.js (vulnerable, this app)
store.log(`Login attempt username=${username} password=${password}`); // logs the raw password

Attack scenario: click "Trigger a login attempt" above with any username/password, then "View server logs" — the password you typed is sitting there in plaintext, exactly as a real debug log left enabled in production would expose it.

Variant 10 — Sensitive Data Exposed in a URL (Query String) CWE-598

Mechanism: a security token (session ID, password-reset code, API key) is placed in a URL's query string rather than a request body, header, or cookie.

Impact: URLs are logged by web servers, reverse proxies, and CDNs by default; they're stored in browser history and autocomplete; and if the page ever links to a third-party resource, the full URL — token included — can leak via the Referer header.

Node.js — routes/a04.js (vulnerable, this app)
const magicLink = `/api/a04/magic-login?token=${token}&email=${encodeURIComponent(email)}`;
store.log(`GET ${magicLink} 200 — (simulated access log entry)`); // token now lives in the access log too

Attack scenario: "Generate magic link" above creates exactly this kind of URL; "View server logs" then shows the token sitting in the access log in plaintext — the same way it would sit in any real reverse-proxy or CDN log by default.

3. Why Common "Fixes" Fail (False Senses of Security)

Myth 1: "It's Base64-encoded, so it's protected."

Base64 (and similarly, XOR "obfuscation," hex, or ROT13-style tricks) is encoding, not encryption — there is no key, and anyone can reverse it in one line of code. Encoding hides data from a glance, not from an attacker.

Myth 2: "We use HTTPS everywhere, so we don't need to worry about crypto elsewhere."

Transport encryption (HTTPS/TLS) only protects data in transit between two endpoints. It does nothing for data at rest in the database, in backups, in logs, or in memory — and does nothing to fix weak hashing, hard-coded keys, or a bad PRNG.

Myth 3: "We hash passwords with SHA-256, so we're following best practice."

SHA-256 is a fast, general-purpose cryptographic hash — exactly the wrong property for passwords. Fast hashes let an attacker who steals the hash database try billions of guesses per second on cheap GPU hardware. Passwords need a slow, memory-hard, purpose-built hash (bcrypt, scrypt, Argon2id) with a tunable work factor and a per-user salt.

4. Architectural Defense

Layer 1 — Classify data, then apply the matching primitive

Decide upfront what's sensitive (PII, credentials, payment data, tokens, health data) and pick the right tool: a slow salted hash for passwords, authenticated encryption (AES-GCM/ChaCha20-Poly1305) with a fresh nonce for data you must recover, and a CSPRNG for anything unpredictable (tokens, session IDs, reset codes).

Layer 2 — Key management, not key hard-coding

Keys belong in a secrets manager or KMS (AWS KMS, HashiCorp Vault, GCP KMS, Azure Key Vault), loaded at runtime, rotated on a schedule, and scoped so a single leak has blast-radius limits.

Node.js — secure password hashing (conceptual)
const bcrypt = require('bcrypt');

// Storing a password
const passwordHash = await bcrypt.hash(plainPassword, 12); // salted + slow, tunable cost factor

// Verifying a password
const ok = await bcrypt.compare(candidatePassword, passwordHash);
Node.js — authenticated encryption with a random nonce (conceptual)
const { randomBytes, createCipheriv, createDecipheriv } = require('crypto');

function encrypt(plaintext, key) {
  const iv = randomBytes(12); // fresh nonce every time — never reused
  const cipher = createCipheriv('aes-256-gcm', key, iv);
  const ciphertext = Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()]);
  const authTag = cipher.getAuthTag(); // detects any tampering with the ciphertext
  return { iv, ciphertext, authTag };
}

Layer 3 — Enforce transport security & secure defaults

Redirect all HTTP to HTTPS, send Strict-Transport-Security, and set Secure; HttpOnly; SameSite=Strict (or Lax) on every session cookie. Use a CSPRNG (crypto.randomBytes/crypto.randomInt) for every token, and never write secrets to logs — scrub them at the logging layer, not by developer discipline alone.
