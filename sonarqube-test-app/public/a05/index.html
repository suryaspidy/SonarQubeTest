Variant 1 — SQL Injection: Authentication Bypass

CWE-89 · POST /api/a05/sql-login

The query is built by string concatenation against a real embedded SQLite database (Node's built-in node:sqlite) — no parameterization.

—
Fix: use parameterized queries / prepared statement bind parameters — never concatenate user input into SQL text.

Variant 2 — SQL Injection: UNION-Based Data Exfiltration

CWE-89 · GET /api/a05/search

A "search users" feature vulnerable to the same flaw — exploited with UNION SELECT to pull rows from an unrelated api_keys table.

—
Fix: parameterized queries, plus least-privilege DB accounts so a compromised query can't reach unrelated tables at all.

Variant 3 — OS Command Injection

CWE-77 / CWE-78 · GET /api/a05/ping

User input is concatenated directly into a real shell command (ping -c 1 <host>).

—
Fix: never build shell commands from user input; use an execFile/spawn call with an argument array (no shell interpretation) and an allow-list of valid hosts.

Variant 4 — Code Injection via eval()

CWE-94 / CWE-95 · POST /api/a05/calculate

A "calculator" evaluates the user's expression directly with eval().

—
Fix: never eval() user input. Use a real, sandboxed expression-only parser (e.g. mathjs in "limited" mode) if arbitrary math is genuinely required.

Variant 5 — Reflected Cross-Site Scripting (XSS)

CWE-79 · GET /api/a05/greet

User input is reflected into the HTML response unescaped. Open it in a real tab to see the script execute (fetch alone won't run it).

—
Fix: HTML-escape all untrusted output by context (HTML body, attribute, JS, URL); prefer a templating engine with auto-escaping on by default; add a Content-Security-Policy.

Variant 6 — Stored Cross-Site Scripting (XSS)

CWE-79 / CWE-80 · POST /api/a05/comments · GET /api/a05/comments

Comment content is stored, then rendered back unescaped for every future visitor.

—
Fix: HTML-escape stored content on render, or sanitize on input with an allow-list-based library (e.g. DOMPurify) if some HTML must be preserved.

Variant 7 — NoSQL Injection (Operator Injection)

CWE-943 · POST /api/a05/nosql-login (raw JSON)

Sending password as an object instead of a string — e.g. {"$ne": null} — smuggles a MongoDB-style query operator straight into the lookup.

—
Fix: validate the type/shape of every field server-side (reject objects where a string is expected) before it ever reaches a query.

Variant 8 — LDAP Injection

CWE-90 · GET /api/a05/ldap-search

The uid parameter is spliced into an LDAP filter — (&(uid=<input>)(objectClass=person)) — with no escaping of ( ) * \.

—

Try uid=alice first (returns just alice), then the payload above (returns everyone).

Fix: escape LDAP special characters ( ) * \ NUL per RFC 4515 before building any filter, or use a library that does this for you.

Variant 9 — XPath Injection

CWE-91 / CWE-643 · POST /api/a05/xpath-login

An XML-backed login lookup built by string concatenation into an XPath-style boolean expression. Inject the same payload into both fields to neutralize the AND.

—
Fix: use parameterized XPath (XQuery/XPath variable bindings), never string-concatenated queries.

Variant 10 — Server-Side Template Injection (SSTI) / Expression Language Injection

CWE-917 / CWE-94 · POST /api/a05/welcome

User input becomes part of the template source, not just a substituted value — embedding {{ }} reaches the template evaluator, including real code execution.

—

Try {{ 7*7 }} first for a harmless arithmetic proof, then the full payload above.

Fix: never let user input become template source; if a template engine is required, run it in a real sandbox with no access to globals/require, or use a logic-less templating language.

Variant 11 — Log / CRLF Injection (Log Forging)

CWE-93 / CWE-117 · POST /api/a05/log-event · GET /api/a05/logs

Unneutralized newlines in user input let an attacker forge fake extra log lines. (Node itself blocks raw CRLF in real HTTP headers — see the Learn modal — so this demo targets application logs instead, which have no such built-in protection.)

—
Fix: strip or encode CR/LF (and other control characters) from any value before writing it to a log, or use a structured logger (JSON lines) where a forged value can't create a new "line".

📘 Deep Dive: OWASP A05:2025 — Injection

Injection sits at #5 in OWASP's Top 10:2025 (down two spots from #3 in 2021). It's one of the most heavily tested categories — 100% of applications tested showed some form of injection — and it has more mapped CWEs (37) and more total CVEs than any other 2025 category.

Cross-site Scripting (CWE-79) alone accounts for over 30,000 of those CVEs (high frequency, lower average impact); SQL Injection accounts for over 14,000 (lower frequency, higher average impact) — together they pull the category's average weighted impact down even though individual SQLi incidents are often severe.

1. What Counts as "Injection"?

Per OWASP: an injection flaw lets untrusted input reach an interpreter — a browser, a database, the command line, an LDAP server, a template engine — and causes that interpreter to execute part of the input as commands, rather than treating it purely as data. An app is vulnerable when:

  • User-supplied data is not validated, filtered, or sanitized.
  • Dynamic queries or non-parameterized calls without context-aware escaping are used directly in the interpreter.
  • Unsanitized data is used within ORM search parameters to extract additional, sensitive records.
  • Hostile data is directly concatenated so the interpreter's structure and the data are mixed together in one string.

Common injection targets, per OWASP's own description: SQL, NoSQL, OS command, ORM, LDAP, and Expression Language (EL) / OGNL injection — "the concept is identical among all interpreters." A related, newer class — LLM Prompt Injection — is significant enough that OWASP now tracks it separately in the OWASP LLM Top 10 rather than folding it in here.

2. The Variants

This lab implements 11 variants, covering every injection target OWASP names by name, plus both forms of XSS. Expand each for the mechanism, vulnerable code, and how it's exploited:

Variant 1 — SQL Injection: Authentication Bypass CWE-89

OWASP Example Attack Scenario #1 (adapted): String query = "SELECT * FROM accounts WHERE custID='" + request.getParameter("id") + "'"; — an attacker sends ' OR '1'='1 and the query's meaning changes to "return everything."

Node.js — routes/a05.js (vulnerable, this app)
const query = \`SELECT id, username, role FROM users WHERE username = '\${username}' AND password = '\${password}'\`;
const row = db.prepare(query).get(); // real SQLite, no parameterization

Attack scenario: submitting username = ' OR '1'='1' -- turns the query into ...WHERE username = '' OR '1'='1' --' AND password='...' — the trailing -- comments out the password check entirely, logging in as the first user in the table with no valid credentials at all.

Variant 2 — SQL Injection: UNION-Based Data Exfiltration CWE-89

Mechanism: the same unparameterized-query flaw, but exploited with UNION SELECT to append rows from a completely different table onto the legitimate result set.

SQL — exploit payload
SELECT username, role FROM users WHERE username LIKE '%' UNION SELECT service, key_value FROM api_keys --%'

Attack scenario: the response above disguises leaked Stripe/AWS API keys as extra "username"/"role" rows — proving that even a low-sensitivity endpoint (a user search box) can leak data from tables it was never designed to touch, entirely because of one string-concatenated query.

Variant 3 — OS Command Injection CWE-77 / CWE-78

OWASP Example Attack Scenario #3: String cmd = "nslookup " + request.getParameter("domain"); Runtime.getRuntime().exec(cmd); — an attacker supplies example.com; cat /etc/passwd to run arbitrary commands.

Node.js — routes/a05.js (vulnerable, this app)
exec(\`ping -c 1 \${host}\`, (err, stdout, stderr) => { /* ... */ }); // host is user input

Attack scenario: submitting host = 127.0.0.1; whoami runs two commands — the intended ping AND the attacker's injected whoami — because the shell treats ; as a command separator, not part of a hostname.

Variant 4 — Code Injection via eval() CWE-94 / CWE-95

Mechanism: a feature meant to evaluate simple math expressions passes user input directly to eval(), which executes arbitrary JavaScript, not just arithmetic.

Node.js — routes/a05.js (vulnerable, this app)
const result = eval(expression); // expression is fully attacker-controlled

Attack scenario: instead of 2+2, the attacker sends require('os').hostname() or worse — require('child_process').execSync('id') — turning a calculator into full Node.js code execution.

Variant 5 — Reflected Cross-Site Scripting (XSS) CWE-79

Mechanism: a query parameter is written directly into the HTML response with no escaping, so a <script> tag in the URL executes in the victim's browser exactly as if the site itself wrote it.

Node.js — routes/a05.js (vulnerable, this app)
res.send(\`<h1>Hello, \${name}!</h1>\`); // name is the raw query parameter

Attack scenario: an attacker sends a victim a link like /api/a05/greet?name=<script>...</script>. The victim's own browser, in the site's own origin, runs the attacker's script — able to read cookies, make authenticated requests, or deface the page.

Variant 6 — Stored Cross-Site Scripting (XSS) CWE-79 / CWE-80

Mechanism: the same missing-escaping flaw, but the payload is saved server-side first (a comment, a profile field, a support ticket) and then rendered to every visitor who views that content later — no per-victim link required.

Node.js — routes/a05.js (vulnerable, this app)
const html = comments.map(c => \`<div>\${c}</div>\`).join(''); // c is raw stored input

Attack scenario: one attacker posts a malicious comment once; from then on, every visitor who opens the comments page runs the attacker's script in their own session — far more impactful than reflected XSS since no individual targeting is needed.

Variant 7 — NoSQL Injection (Operator Injection) CWE-943

Mechanism: a document-database query is built directly from parsed JSON request fields. Since JSON supports objects as values, a client can send {"password": {"$ne": null}} instead of a string — and a query layer that doesn't validate types honors the operator.

Node.js — data/injection-store.js (vulnerable, this app)
if ('$ne' in v) return doc[k] !== v.$ne; // no check that v was ever supposed to be an object

Attack scenario: a normal login form only ever sends strings, so the developer never validates the type — but nothing stops a client from posting raw JSON with password as an object, turning "password not equal to null" (always true for a real password) into an automatic bypass.

Variant 8 — LDAP Injection CWE-90

Mechanism: an LDAP search filter — parenthesized prefix notation like (&(uid=alice)(objectClass=person)) — is built by splicing raw input into the uid= term, with none of LDAP's required special-character escaping.

Node.js — data/injection-store.js (vulnerable, this app)
const filterStr = \`(&(uid=\${uidInput})(objectClass=person))\`; // uidInput unescaped

Attack scenario: the classic payload *)(uid=*))(|(uid=* injects extra, unbalanced parentheses that restructure the filter's logic entirely — turning "find the one user named X" into "find everyone," returning the full directory instead of a single record.

Variant 9 — XPath Injection CWE-91 / CWE-643

Mechanism: the same string-concatenation flaw as SQL injection, applied to an XPath-style boolean expression used to query an XML-backed data store.

Node.js — data/injection-store.js (vulnerable, this app)
const expr = \`username='\${username}' and password='\${password}'\`; // then evaluated as a boolean expression

Attack scenario: injecting x' or '1'='1 into both fields turns the expression into one that's true regardless of the real stored values — username='x' or '1'='1' and password='x' or '1'='1' is true the moment either trailing '1'='1' clause is reached, authenticating as the first user with no valid credentials.

Variant 10 — Server-Side Template Injection (SSTI) / Expression Language Injection CWE-917 / CWE-94

Mechanism: user input is concatenated into the template's source string before it's rendered — so a value like {{ 7*7 }} isn't just displayed, it's evaluated by the template engine as an expression.

Node.js — routes/a05.js + data/injection-store.js (vulnerable, this app)
const template = \`Hello, \${name}! Welcome back.\`; // name becomes part of the SOURCE
const rendered = naiveTemplateRender(template, { name, require }); // require exposed in scope

Attack scenario: {{ 7*7 }} proves expression evaluation (renders "49"); {{ require('child_process').execSync('whoami') }} proves full remote code execution — because this template engine's evaluation context accidentally exposes Node's require, a real, well-documented escalation path in vulnerable Node template engines/sandboxes.

Variant 11 — Log / CRLF Injection (Log Forging) CWE-93 / CWE-117

Mechanism: user input containing raw newline characters is written directly into a log line. Since a log viewer treats each newline as a new entry, the attacker can make it look like a second, entirely fabricated log line was written by the server itself.

Node.js — routes/a05.js (vulnerable, this app)
store.logAudit(\`[AUDIT] Login attempt for user: \${username}\`); // username may contain \n

Attack scenario: submitting a username of attacker\n[AUDIT] Login attempt for user: admin (verified by security team) creates what looks like two separate, legitimate-looking audit entries — useful for covering tracks or framing another account during an incident investigation.

Classic HTTP response splitting (injecting a real extra HTTP header via CRLF in a header value) is blocked by Node's http module itself on modern versions (it throws ERR_INVALID_CHAR) — a good example of a whole vulnerability class being closed off at the platform level. Application-level logs have no equivalent built-in protection, which is why this variant targets those instead.

3. How to Prevent It (per OWASP)

The best defense keeps data separate from commands/queries entirely:

  • Use a safe API that avoids the interpreter entirely, provides a parameterized interface, or migrates to an ORM. Note: even parameterized stored procedures can reintroduce SQL injection if they concatenate query text internally or use EXECUTE IMMEDIATE/exec() on hostile data.
  • When separation isn't possible: positive server-side input validation (not a complete defense alone, since many apps legitimately need special characters).
  • For any residual dynamic queries: escape special characters using the specific escape syntax for that interpreter. Note: structural elements like table/column names can't be escaped — user-supplied structure names are inherently dangerous (a common issue in report-writing software).

OWASP's own warning: manual escaping/parsing of complex strings is error-prone and fragile against minor changes to the underlying system — safe APIs and parameterization are strongly preferred over hand-rolled escaping.
